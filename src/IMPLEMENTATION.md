# V3 implementation

This document describes the implemented design and its trade-offs. Use the [developer guide](README.md) for API contracts and deployment. V3 is an internal licence-key service; it deliberately has no dashboard or feature-entitlement layer.

## Audit alignment

The supplied audit and linked reports were reviewed against the current checkout rather than treated as an authoritative inventory. The checkout already used Drizzle, exact numeric storage, hashed credentials, transactional idempotency, trusted-proxy parsing and fail-closed dependency checks. The audit proposed moving from Drizzle to Prisma; the user's decision to retain Drizzle supersedes that proposed migration.

User decisions superseded proposals to remove users, introduce shared feature entitlements, use private-by-default custom metadata, use SSE, or retain compiled-application distribution. Groups and users remain optional associations. Public validation exposes licence-domain data including raw registrations, with administrative notes recursively excluded. Ordinary API keys need explicit consumption permission and group access; the environment master retains unrestricted permissions. Licence credentials cannot consume. Integration streaming uses WebSocket. Source/Bun container deployment replaces application compilation.

Confirmed code defects and substantiated risks drove changes to authority checks, permission defaults, webhook ownership/egress/signing/retries, request admission, mutation/replay concurrency, response validation and operational tooling. Performance claims that require workload measurements remain recommendations: no throughput benchmark or claim of unlimited scalability follows from static review.

## Structure and runtime

[main.ts](main.ts) dispatches version, master-key, healthcheck, migration and serve commands. Dynamic imports keep lightweight commands independent of database/Redis/server configuration. [Config](core/config/Config.ts) validates command-specific settings and reports setting names without secret values. [ServerServices](core/ServerServices.ts) composes explicit service dependencies; [app.ts](app.ts) composes Elysia routes.

[ServerLifecycle](core/ServerLifecycle.ts) verifies migration history, connects dependencies and initialises event publication before listening. Serving never applies migrations. Publication and webhook delivery run independently, with separate in-flight tracking and capped exponential backoff after failures. Maintenance runs in UTC. Shutdown stops admission and new work, closes streams, aborts webhook transport with unknown-outcome retry evidence, drains HTTP/background settlement promises, then closes dependencies; a 25-second forced deadline is visible in logs.

The exact Bun canary is pinned by `.bun-version`, `.bun-revision` and `packageManager`. [Doctor](scripts/doctor.ts) detects drift. Elysia 2 beta and Drizzle release-candidate versions are retained deliberately; compatibility is assessed through the actual pinned code and focused/runtime checks rather than rejected solely because of their release labels.

## Request boundaries and authority

[RequestService](core/http/RequestService.ts) enforces a per-process in-flight cap, fixed URL/header bounds and Redis-backed direct-peer rate admission before parsing/database work. Behind a proxy, that initial budget is shared by the proxy's direct address; authenticated/client-IP limits apply later. JSON parsing has a 1 MiB cap and a request deadline. [InputPolicy](core/http/InputPolicy.ts) validates exact decimals, timestamps, Unicode, metadata size/depth and bulk input before storage.

[HttpBoundary](core/http/HttpBoundary.ts) maps failures to consistent typed responses and safe details. [Response](core/http/Response.ts) wraps validated payloads. Elysia 2 beta runs `mapResponse` before its normal response validation and bypasses validation for native `Response` instances; the wrapper therefore invokes the public response validator on the original payload before producing the envelope. This preserves route-specific schemas rather than accepting any JSON shape. OpenAPI generation applies the same public envelope, including the health-503 diagnostic/error union.

[AuthService](core/auth/AuthService.ts) recognises the environment master separately from persisted API keys. API-key resources never contain the master. Stored credentials are hashed; issuance/rotation discloses plaintext once. New keys have no scopes or groups and start disabled. Only the master manages API keys and operational settings, so ordinary principals cannot mint or widen their own grants.

The [operation registry](core/http/operations.ts) explicitly admits mounted HTTP operations and supplies reference authority/idempotency metadata. Unregistered requests fail closed. Licence detail is an explicit `licenses:read` composite of administrative state, counters and registrations. Counter-definition updates also require `usage:adjust`; accepted historical usage has its own `usage:read` lookup.

Action checks are repeated inside service transactions against the current key row, held with a shared row lock until that transaction ends. Grant changes, disable/delete and rotation wait for already-authorised transactions; later transactions see the change. Group predicates filter database reads before pagination, and writes recheck source/destination associations. Ungrouped resources require all-group access. User mutations require all-group authority because users may span groups. Cascading operations require authority for their effects.

[EventAuthorization](core/auth/EventAuthorization.ts) maps known event types to resource-read permissions without a fallback grant for unknown types. Event history, WebSocket batches and webhook work also apply current group/global restrictions. Network delivery uses a checked snapshot: revocation cannot recall a batch or webhook already sent or in flight.

Combined transfer evidence retains every historical group whose values it contains. Both-group authority is required for before/after counter history, including queued webhook delivery and manual replay; transfers involving ungrouped data require all-group access. Redacted attach/detach notifications remain available to the individual affected group. Webhook lifecycle events, like API-key and settings lifecycle events, are master-only: a webhook read grant for one's own endpoints never grants other owners' control-plane activity.

## Persistence, locks and migrations

[Drizzle schema](core/database/schema/) is authoritative. PostgreSQL stores resource state, exact counters, audit evidence, durable events, delivery attempts and retry identities. Redis supplies shared admission/rate state and stream leases; it is not the persistent licence database.

[Database](core/database/Database.ts) uses reserved connections, bounded acquisition/statement/lock/transaction deadlines and fail-closed error mapping. The existing shared/exclusive topology advisory lock is retained deliberately: normal work takes shared topology authority, while parent and permission topology mutations use exclusive coordination. Licence row locks serialize consumption and registration. Stable resource lock order reduces deadlocks. This favors clear invariants but can constrain unrelated operations during topology writes; its performance cost remains unmeasured and should be profiled before replacement.

Operations with durable retry identities may retry complete transactions up to twice for PostgreSQL `40001` or `40P01`, within the original deadline. Those errors prove rollback. Lost connection or COMMIT acknowledgement is never treated as permission to repeat an unkeyed mutation; callers recover the recorded operation instead.

[MigrationService](core/database/MigrationService.ts) has two paths. `verify()` holds a bounded shared migration lock and compares exact history names/timestamps/hashes without schema changes. `run()` is an explicit migrator operation with an exclusive migration lock, bounded lock/statement waits and transactional pending SQL/history writes. Nonempty unversioned databases and modified/newer histories are refused without clearing data. Session timeout settings are restored before releasing the reserved connection.

The fresh v3 SQL baseline intentionally represents the undeployed beta schema. Existing incompatible history is not silently reinterpreted. Applied migrations are immutable. [Schema verification](scripts/check-migrations.ts) independently generates fresh SQL, applies generated and committed definitions to separate disposable databases, then compares catalog columns, defaults, constraints, indexes, enums, triggers, sequences, functions and policies. It also detects migration side effects on cluster-wide role authority; deployment privilege tests cover runtime grants. This detects SQL/snapshot drift rather than relying on generator filenames alone.

[Compose](../compose.yml) uses administrator, migrator and runtime credentials with distinct roles. The migrator owns application schema; runtime has no DDL or migration-history writes. Migrations revoke runtime UPDATE/DELETE on audit and accepted-usage history. Events remain mutable by the publisher to assign sequence/published state. Operators provisioning their own roles must preserve equivalent grants; application authorization complements database privileges.

## Validation and usage

[ValidationService](plugins/validate/ValidationService.ts) takes a shared licence lock, reads PostgreSQL time, applies [eligibility rules](plugins/validate/Eligibility.ts) and returns a consistent [full view](plugins/licenses/LicenseView.ts). It neither consumes usage nor registers identities. Group/user state, expiry, expected group/user and registered-device/IP policies determine eligibility. Counter exhaustion does not. Disabled keys expose their custom reason; malformed/unknown secrets disclose no resource.

The bearer projection intentionally includes linked records, metadata and raw registration IDs for anyone with the licence credential. It excludes administrative notes from licence, group and user projections. Administrative reads use their separate permissioned projection. Keyzori cannot enforce how an integration stores a credential or whether it honors the returned decision.

[MeterService](plugins/licenses/MeterService.ts) keeps values as exact decimal strings backed by PostgreSQL numeric operations. Consumption locks the licence, applies due resets, checks all requested increments and commits all counters, audit/event records and an immutable accepted-usage operation together. It rejects increments beyond a configured limit; no implicit overage exists. Administrative adjustment is a distinct permission and audited action.

Consumption retry identity is permanently unique by licence/principal/idempotency key in [usage_operations](core/database/schema/usageOperations.ts). Fingerprints bind the original input; current authority and eligibility are checked before replay. Retained receipts survive counter changes and licence credential rotation, and historical evidence survives entity deletion. Permissioned historical lookup is separate from replay eligibility: an accepted operation remains investigable after lifecycle changes without authorising another consumption. There is no automatic accepted-ledger pruning.

[IdempotencyService](core/security/IdempotencyService.ts) separately handles administrative receipts with a 24-hour default retention. It serializes receipt identity with transaction advisory locks, rechecks authority and fingerprints the input/authority. Reuse with different content conflicts. Secret issuance stores recovery IDs rather than replayable plaintext. Expired administrative receipts can permit a new operation, unlike consumption's retained ledger identity.

Deletion receipts retain their resource/group/ownership authority. Replay authenticates current permissions against that historical context without requiring deleted rows to still exist. Receipt recovery does not bypass revocation or expose another principal's operation.

[MeterSchedule](plugins/licenses/MeterSchedule.ts) derives calendar boundaries using PostgreSQL, with UTC as the default timezone. Intervals are half-open, month-end dates clamp, and `schedule.anchorAt` supplies a recurring local calendar phase. Counter-level `startsAt` independently blocks consumption before an absolute instant without invalidating the licence. Stable counter IDs, definition revisions, reset generations and period identities accompany usage evidence. Validation projects overdue usage as zero without writing it. Mutations and maintenance persist one catch-up reset for the current period. Scheduled and execution timestamps remain distinct; the developer guide specifies DST behavior and defaults.

## Events, webhooks and audit evidence

Domain transactions append durable integration event payloads. A short publisher transaction locks event-state metadata and assigns monotonic sequences only to committed visible rows. Readers order by publication sequence, avoiding a cursor that skips a transaction merely because it allocated an earlier identifier and committed later. Payloads have schema version and stable event IDs. Ordering is publication order, not a promise of wall-clock commit order.

[ActivityService](plugins/activity/ActivityService.ts) serves bounded replay pages and WebSocket batches with fresh permission checks. Cursors bind a stream epoch, sequence and principal grant fingerprint. Redis leases cap shared principal/IP admission; local limits, subscribe deadlines, session expiry and backpressure cap each process's exposure. Persisting processed cursors and deduplicating events belongs to the receiver. Failed admission or dependency renewal closes rather than reporting a healthy live stream.

`GET /events/watermark` starts the invalidation/refetch/replay synchronization protocol; it is a publication checkpoint, not an atomic resource snapshot. Optional event retention prunes only a safely published prefix already passed by enabled webhooks. The offline `prepare-restore --confirm-restored-database` command verifies schema history, changes the epoch and audits/disables/cancels restored webhook work before replicas resume. Ordinary startup never changes the restore epoch or silently repairs delivery state.

[WebhookService](plugins/webhooks/WebhookService.ts) captures ownership and permitted event/group selection. URL/filter changes disable endpoints and cancel pending work; explicit re-enabling starts at the current publication position. Per-endpoint backlogs and global endpoint count are bounded. [WebhookDispatcher](plugins/webhooks/WebhookDispatcher.ts) uses row locks, claim tokens and expiring leases, checks owner authority before dispatch and fences settlement by claim token. Sends occur outside database transactions.

[WebhookTransport](plugins/webhooks/WebhookTransport.ts) defaults to public HTTPS egress, vets DNS addresses, pins the connection, verifies TLS identity, rejects redirects and bounds time/body exposure. Operator-only private destination exceptions require both an exact origin and an approved actual-address CIDR; API permissions cannot widen them. [WebhookSecrets](plugins/webhooks/WebhookSecrets.ts) encrypts recoverable signing secrets under a separate operator key. Queued deliveries snapshot their signing key; rotation does not invalidate their verification. Retries are bounded and at least once. Claim fencing prevents stale settlement from overwriting a newer claim, but cannot prove that a timed-out receiver did not execute a side effect.

[AuditService](plugins/audits/AuditService.ts) records mutation evidence in the same transaction as changes. Operational request logs are structured diagnostics with safe IDs/codes; integration events are durable messages for subscribers. These are distinct records with different purposes. Failure evidence is bounded and rate-gated. Audit and accepted-usage identity are retained indefinitely; events are retained indefinitely by default with separate optional safe-prefix pruning. Maintenance uses configurable row/time/observation budgets, per-record failure backoff and bounded cleanup, preserving pending work without repeatedly starving healthy records behind a failing prefix.

## Packaging and verification

The [Dockerfile](Dockerfile) installs the exact pinned Bun runtime and production dependency lock, then runs TypeScript source as a non-root user. There is no application compilation or executable release requirement. Reference generation uses typed inert dependencies and fails rather than contacting runtime services.

[Test services](scripts/test-services.ts) create uniquely named/labelled disposable PostgreSQL and Redis containers, cancel interrupted startup, enforce subprocess/cleanup deadlines and remove inspected immutable container IDs owned by that invocation. All cleanup branches are attempted even when another fails. Diagnostics redact credentials; structured internal stdout is preserved for parsing. The shared [runtime contract](tests/fixtures/RuntimeContract.ts) exercises exact consumption/replay, rotation, bearer projections, credential secrecy, WebSocket reconnect/revocation and shutdown. Linux source and exact-image checks use a separately isolated real HTTPS receiver without weakening production egress policy. Compose adds restricted role and persistence checks. These checks must actually run before those properties are claimed verified for a release.

[Server CI](../.github/workflows/server.yml) targets Linux AMD64 and ARM64 and includes workflow validation, runtime/type/lint/schema/tests, OpenAPI and smoke checks. [CodeQL](../.github/workflows/codeql.yml) also runs on `v3`. Publishing is gated to checked `main` commits and immutable tagged revisions; `v3` pushes cannot enter that path. [Release policy](../.github/RELEASE_POLICY.md) uses version tags and disables automatic latest promotion. Commit, CI, release and deployment remain separate actions.

### Bounded query measurements

The isolated PostgreSQL 18 fixture contains 8,000 licences, 16 skewed groups, 200 users and timestamp ties/null expiries. Three cache-warm `EXPLAIN (ANALYZE, BUFFERS)` samples per query showed created-descending first-page scans fall from 8,000 to 51 rows (median 1.700 ms to 0.028 ms), and deep created-ascending scans from 6,051 to 51 (0.676 ms to 0.033 ms). These are database execution measurements for this fixture, not end-to-end latency or a production SLO.

Licence collections use five Drizzle statements for root and eight for selected-group callers at page sizes 1/50/100. Detail projections with two/eight identical overdue schedules both use 13 statements after request-local reuse, versus 15/27 before. Counts exclude native transaction commands and HTTP authentication. Metadata/substring filters still scan this fixture; a selected-group `IN` head page also has a measured optimizer trade-off (1,566 timestamp-index scan rows versus the prior 240-row bitmap plan). No speculative metadata or trigram indexes were added.
